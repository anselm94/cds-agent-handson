# Day 15 (Part 2): Content Filtering & Data Privacy

Day 15 split the monolith into three agents. This last stretch (the remaining 20% of time) is about **trust and privacy**: making sure the agent refuses unsafe content and does not leak sensitive data.

Both safeguards are configured in one place — the **orchestrator's model** in `orchestrator-agent/agent.js`. That is the single entry point, so every request (and every sub-agent response that flows back through it) is covered.

We add two concerns to the `OrchestrationClient`:

| Concern           | What it does                                | Config      | Provider                     |
| ----------------- | ------------------------------------------- | ----------- | ---------------------------- |
| Content filtering | Blocks unsafe prompts and model outputs     | `filtering` | Azure Content Safety         |
| Data masking      | Detects and anonymizes sensitive data (PII) | `masking`   | SAP Data Privacy Integration |

---

## Step 5 - Content filtering (Azure Content Safety)

Add the two builder imports from the orchestration package:

```javascript
import {
  buildAzureContentSafetyFilter,
  buildDpiMaskingProvider,
} from "@sap-ai-sdk/orchestration";
```

Then add a `filtering` block to the `OrchestrationClient` config:

```javascript
filtering: {
  // content filtering for input and output to ensure safe content handling
  input: {
    filters: [
      buildAzureContentSafetyFilter("input", {
        violence: "ALLOW_SAFE_LOW",
        prompt_shield: true, // prompt attack mitigation
      }),
    ],
  },
  output: {
    filters: [
      buildAzureContentSafetyFilter("output", {
        violence: "ALLOW_SAFE_LOW",
      }),
    ],
  },
},
```

Notes:

- **`input` vs `output`** — the enum value passed to `buildAzureContentSafetyFilter` selects what is scanned: the incoming prompt, or the model's generated response.
- **Thresholds** — the jump level per category ranges `ALLOW_SAFE` (strictest) → `ALLOW_SAFE_LOW` → `ALLOW_SAFE_LOW_MEDIUM` → `ALLOW_ALL`. `ALLOW_SAFE_LOW` is a moderate default.
- **`prompt_shield`** (input only) — enables prompt-attack/jailbreak detection, not just offensive-content detection.

---

## Step 6 - Data masking (SAP Data Privacy Integration)

Add a `masking` block to the same config:

```javascript
masking: {
  masking_providers: [
    buildDpiMaskingProvider({
      // sap data privacy integration for anonymization/pseudoanonymization of sensitive data
      method: "anonymization",
      entities: [
        "profile-person",
        "profile-address",
        "profile-email",
        "profile-username-password",
      ],
    }),
  ],
},
```

Notes:

- **`method`** — `anonymization` (irreversible) or `pseudonymization` (reversible). Here we anonymize.
- **`entities`** — the classes of data DPI scans for and masks (e.g. `profile-person`, `profile-email`). The full list includes many more (`profile-phone`, `profile-iban`, `profile-ssn`, `profile-credit-card-number`, …).
- **Flow** — masking runs on the request *before* it reaches the model, and is re-identified on the response, so the model never sees the raw PII.

## Full model config

Here is the complete `new OrchestrationClient({...})` after both steps:

```javascript
const model = new OrchestrationClient({
  promptTemplating: {
    model: {
      name: "gpt-5.4",
    },
  },
  filtering: {
    input: {
      filters: [
        buildAzureContentSafetyFilter("input", {
          violence: "ALLOW_SAFE_LOW",
          prompt_shield: true,
        }),
      ],
    },
    output: {
      filters: [
        buildAzureContentSafetyFilter("output", {
          violence: "ALLOW_SAFE_LOW",
        }),
      ],
    },
  },
  masking: {
    masking_providers: [
      buildDpiMaskingProvider({
        method: "anonymization",
        entities: [
          "profile-person",
          "profile-address",
          "profile-email",
          "profile-username-password",
        ],
      }),
    ],
  },
});
```

## Key concepts

- **Orchestrator-level** — filtering and masking are configured once, on the orchestrator's model, *before* any sub-agent is invoked. They are not repeated in `bookshop-agent` or `salesorder-agent`.
- **Content safety ≠ data privacy** — filtering *blocks* unsafe content (blocks the call); masking *transforms* sensitive values (replaces, then re-identifies). They are independent, complementary layers.
- The two builders come from `@sap-ai-sdk/orchestration`, a transitive dependency of `@sap-ai-sdk/langchain` (already resolves — no `package.json` change needed).
